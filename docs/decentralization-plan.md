# MostBox 长期方案与推进计划

更新日期：2026-11-22。本文记录负责人确认的长期目标、设计原则和推进顺序。

长期方向以本文为准；[开发与发行路线](roadmap.md)管理客户端与发行范围，[验收指南](acceptance.md)定义执行标准，[验证状态](validation-status.md)记录已有证据。目标与计划不代表已经实现或通过验收。

## 目标

**MostBox 的最高目标是成为能脱离创始人长期存在的公共协议。** 即使创始人永久退出，第三方仍能理解、实现、运行、维护和继续发展它。

协议服务于去中心化聊天与文件传输，参考客户端保持**聊天第一，文件第二**。品牌、官方客户端、公司规模和商店覆盖都不作为协议存续的前提。每项投入都要说明它解决的真实需求，以及是否减少对创始人的知识、资产或批准的依赖。

群聊规则统一见[群聊模型与消息承诺](chat-model.md)：仅普通用户一种群内身份，产品只使用一个 `channelId` 标识并加入群，历史平权、维护志愿，私密群凭据泄露后换群；可猜的公开群作为公开讨论入口。文字默认同步保存，附件点击时下载，校验后默认继续做种。消息只显示哪些用户收到，不做已读；对方客户端收到即算，回执机制待设计。

2026-11-22 确认：群体自行维持持续可用性，建议群内愿意维护的成员自建常在线服务器节点，加入群并保存、同步文字消息，帮助错峰上线的成员补齐。服务器节点仍是普通成员，维护者没有额外群权限；不要求每位成员自建，也不依赖创始人托管。没有可达消息副本时等待持有者上线，不承诺随时送达或永久保存。纯中继不自动保存群消息；服务器节点也不自动下载全部附件。

## 首批用户与使用场景

2026-11-22 确认：首批用户是愿意搭建远程节点、供朋友或公众使用的人；朋友及公众使用者通过这些节点参与聊天和文件传输。维护意愿来自自身与群体的通信需求，沿用维护自愿、群内平权与附件按需下载的规则。

产品体验目标是提供像微信一样方便的聊天与文件传输。完全去中心化的长期目标依照下述成功标准验收：第三方可独立实现、基础设施可接替、群体自主运行、维护与分发可交接。自建服务器是群体承担运行责任的方式，当前尚未完成整体验收。公开提供节点与公开群的加入值分别描述；节点访问控制仍独立于群内权限，不在本次定位讨论中新增开放接入机制。

## 用户数据自管与节点替换

2026-11-22 确认：用户自己保管身份与数据。用户须能保留身份恢复材料、已加入群的 `channelId`、已同步文字和已下载文件，原节点永久下线且运营者不配合时，仍能恢复原身份、进入原群、读取自己保存的内容，并连接其他可用节点继续使用。文字默认保存到用户自己的设备，远程节点不成为已有数据的唯一保存位置。

完整保存、导出和恢复方案须先设计，再按[群模型与消息状态验收](acceptance.md#群模型与消息状态验收)执行同一目标版本的节点永久退出演练；现有账号备份不据此视为已覆盖完整历史与文件。未取得且没有其他可用副本的内容不承诺恢复，附件仍按需下载；早期历史版本兼容策略保持不变。

恢复责任已确认：用户负责保管，产品负责让保存、备份和恢复足够简单，支持主动导出备份并在新设备恢复。所有身份恢复材料和可用设备都丢失时，重新建立身份，官方没有重置原身份的权限。身份恢复与消息、文件恢复分开说明，保存内容副本不能代替保管身份恢复材料。

空间与清理边界已确认：空间不足时如实提示，由用户主动清理，不静默删除已有聊天记录或文件，无法保存时不得报告保存成功。删除仅作用于用户选择的本机副本，说明可能停止本机做种及再次获取依赖其他可用副本；不承诺全网删除或删除后必能恢复。具体清理入口、容量处理与删除后同步行为仍待设计和验收。

## 早期协议兼容策略

2026-11-21 确认：项目仍在早期，未来较长阶段不承担历史版本兼容，撤销此前“0.8.0 最后一次不兼容升级、此后永久冻结”的决定。现行实现仍为 v2，新的策略允许后续按需求调整协议，不代表本次已经改动代码。

- 不默认增加兼容分支、新旧协议并存、双写或旧数据迁移。现有版本的升级记录保留为该次升级证据，不作为未来兼容承诺；不因不兼容策略自动清除用户数据。
- 不兼容变更须有清晰版本边界，更新规范、向量、客户端和同版本互通验收，说明旧节点无法互通时如何升级或重建；不让不兼容帧与数据被错误接受。
- 安全与内容身份约束仍按目标版本检查，不因放弃兼容而放宽签名、CID 校验或授权。独立实现验收绑定具体规范版本。
- 何时进入稳定兼容阶段以后另行确认，不预先指定冻结版本。公共协议的长期目标保持不变。

## 成功标准

1. **知识可交接。** 第三方只依靠公开规范、测试向量和明确的上游依赖，就能实现兼容节点；必须询问作者才能解决的歧义要补回规范。
2. **运行可接替。** 官方域名、服务器和更新服务不可用时，第三方仍能部署必要基础设施，已有群体继续通信，空数据目录的新节点也能加入。
3. **维护可延续。** 兼容实现、分发和节点运营不需要创始人批准；提案、决策理由和兼容性证据公开，维护与发布工作可以由其他人接手。
4. **核心可承担。** 协议只规定互通、授权、完整性与演进所必需的行为；界面、平台便利功能和运营服务由各实现选择，不要求复制官方产品。
5. **参与有实际需要。** 群体因为自身通信和文件需求愿意维护节点；第三方能完成部署、恢复与维护，不以创始人持续救场维持使用。

公共协议允许各方维护自己的实现和扩展；访问频道和文件仍遵守既有能力凭证与签名规则。以上标准的执行方式见[公共协议独立性验收](acceptance.md#公共协议独立性验收)，目前尚未完成整体验收。

## 设计原则

1. **三个自证明的标识符，其余都由它们派生。**
   - 内容 = CID（UnixFS CID v1，与 kubo 一致）
   - 频道 = 一把随机密钥
   - 人 = 一把公钥
2. **一种角色：节点。** 在线的节点做三件事：做种它持有的文件，同步它加入的频道；公网可达且主人愿意时，替别人转发字节。手机是经常不在线的节点。不为"种子""中继""常驻节点"各建一套概念。
3. **没有必须由创始人运营的服务器。** 引导、中继、分发等服务须可由第三方接替；种子列表、已知节点缓存和 DHT 发现是阶段 3 的目标，当前能力以实现与验收证据为准。需验证新节点冷启动，不能只验证既有节点继续通信。
4. **知道即有权。** CID、频道密钥、未公告的中继公钥都是能力凭证：知道它就能用，不另建白名单或注册流程。
5. **早期允许不兼容迭代。** 以清楚、可实现的当前协议为目标，不为历史版本维持兼容负担；协议变更有版本、规范、向量与验收证据。
6. **如实写明限制**，不绕过去。见「已知限制」。
7. **用独立实现检验规范。** 共享本仓库生产核心的两个客户端不能证明规范已能被第三方独立实现；可以复用公开上游协议库，但须列明依赖和实际覆盖范围。

- 先设计公共协议独立性验收与独立实现范围，再实现相应工具。保持既有 F1–F5、C1–C5 和量化门槛，不以独立性演练替代可靠性验收。

## 阶段 1：协议规范与独立实现

协议文档与共享测试向量已有初版，现行协议为 v2。下一步用第三方实现检验规范的完整性。

1.1 完善独立实现入口：列清现行必选行为、可选能力、线上编码、错误处理、上游依赖与测试向量；明确 v1 基础章节与 v2 覆盖关系，不把实现路径当作规范正文的替代品。

1.2 【先设计】最小独立实现范围与一致性测试。首个里程碑覆盖频道授权、签名文本同步、`most://` 文件下载校验和下载后做种；明确不支持的可选能力。可复用公开上游库，不复制或调用本仓库生产协议核心，不要求更换语言或重写 Holepunch 栈。

1.3 由未参与该核心实现的第三方依据公开材料完成节点，记录每处需要作者解释的歧义，先补规范和向量，再重放互通测试。维护团队自行写的替代实现可用于准备测试，不据此宣布第三方接手已通过。

验收：独立节点与参考节点双向交换签名消息、互传文件；发布者退出后，全新节点从下载者取得同一 CID 并独立校验。范围、失败案例、原始日志与重放方法一并公开，见[验收指南](acceptance.md#公共协议独立性验收)。

## 阶段 2：协议迭代与版本管理

0.8.0 已完成 v2 升级，规范、该次决策与迁移记录见[协议 v2](protocol/v2/README.md)。后续按本文件「早期协议兼容策略」继续迭代，不再要求这是最后一次不兼容升级。

- 修复实现缺陷与规范歧义时公开问题、影响与目标版本；需要改变协议语义时先更新设计，不静默把参考代码当作规范。
- 变更按 [envelope §7](protocol/v2/envelope.md#7-协议演进规则) 明确版本范围；同版本可选能力仍按现行协商规则使用，不默认维持与历史版本互通。
- 每项提案写明需求、线上字节变化、版本支持范围、旧节点与旧数据处置、测试向量和同版本互通证据。安全问题沿用私下报告渠道。
- 参考仓库是否合入提案，由维护者说明理由；第三方兼容实现和自行分发不以该仓库合入或创始人批准为前提。

## 阶段 3：去掉对创始人的依赖

本阶段补齐可替代的基础设施与冷启动能力；新增公告等协议能力先设计，再明确目标版本与实现验收，不为历史节点默认补兼容分支。

3.1 中继选择

- 【待核实】Hyperswarm 的 `relayThrough` 是否接受函数、能否按连接选择并在失败后回退。
- 选择顺序：用户配置的中继（自己的、好友给的）→ DHT 上公告的 → 安装包自带的种子列表。
- 连不上就换下一个，本次运行内不再使用；本机记住好用的，下次优先。
- 提供"只使用我配置的中继"开关。

3.2 节点成为中继

- 默认关闭，用户主动开启；开启前说明带宽消耗、能看到他人 IP、所在地区可能的法律风险。
- 只有公网可达的节点才能开启，复用已有的可达性检测。
- 公开：在固定的 DHT topic 上公告。私有：不公告，由用户把公钥交给好友。
- `scripts/blind-relay.js` 增加并发会话上限、单个对端会话上限和每会话流量上限，默认值按聊天流量设定并写明依据。

3.3 引导节点

- 【待核实】HyperDHT 是否支持持久化已知节点并用于下次启动、公网 MostBox 节点能否充当引导节点。
- 种子列表可配置；本机缓存见过的好节点。

3.4 移动端

- 中继公钥不再是独立常量；与桌面使用同一套配置和选择逻辑，并可关闭。

3.5 语音

- STUN 地址改为可配置。
- 打洞失败时给出明确提示。

3.6 其他依赖清点

- 列出所有指向创始人或官方服务器的环节（更新检查、下载地址、域名、默认允许的来源等），逐项改为可配置或可缺省，缺失时功能降级而不是失败。

3.7 文档

- `docs/p2p-risk-boundaries.md` 新增志愿中继一节：性质、志愿者的风险、坏中继能做和不能做的事。
- `PRIVACY.md` 写明：公共中继可能由任何人运营，能看到双方 IP、公钥、时间和流量，看不到内容；大量假中继占据公告的风险。
- 大陆商店版是否允许"成为中继"和"使用公共中继"，在合规评估中确定。

验收：在隔离环境中阻断官方域名、服务器、引导、中继与更新服务，第三方从公开保存的源码或安装包部署替代服务，验证已有群体继续通信和空数据目录的新节点加入。引导与中继须由第三方独立运行；仅替换 MostBox 服务、仍依赖默认上游引导节点，不足以证明引导可接替。用志愿节点重跑 F5 的 netns 对称 NAT 条件并达到原门槛，记录实际连接路径和被阻断的依赖。

## 阶段 4：聊天可靠性验收

4.1 按 `AGENTS.md` 的量化门槛建立聊天统计：随机断连、分区、重启注入不少于 100 轮，C1–C4 零违例，分区恢复后收敛时间 P95 不超过 30 秒。

4.2 C5：明确并测试"其他成员全部离线时能读到的历史"。写明常在线节点代收消息的边界：它是频道成员，能读到内容。

4.3 文件验收遗留项：

- F2 坏对端桩：截断、极慢、谎报大小，并测量代价。
- 移动核心的崩溃注入，覆盖范围对齐 `npm run test:crash`。
- 逐连接记录实际路径（直连 / 打洞 / 中继）。
- 排查 real-wifi 重装后第一轮"有 peer 但 0 字节"的失败：先写出复现测试，复现不了就记录已排除的原因。
- 蜂窝与网络切换。

## 阶段 5：整理与分发

5.1 Web3 工具箱移出主仓库。账号密钥派生和设备证书依赖 secp256k1 相关代码，移出时不得影响身份与认证；先列出依赖关系再动手。

5.2 抽出共享协议模块：只搬两端都有的纯函数（CID 与 topic、`most://` 解析、协议消息编解码、频道帧），一次一个模块，不改行为，不拆 `server/src/index.js` 的引擎类。

5.3 统一 `ipfs-unixfs-importer` 版本。先查明移动端停在 17.0.1 的原因；不能统一就把原因写进 `AGENTS.md`。

5.4 分发：源码、可复现的构建和可直接下载的安装包是项目的正本；应用商店版是分发渠道之一，不作为项目存续的前提。

5.5 【先设计】维护与发布交接：公开依赖清单、构建步骤、制品校验与发布流程；第三方用自己的仓库、域名和签名发布可核验的发行版，不共享创始人的私钥、账号或商店凭据。签名变更与用户迁移边界须写明。

5.6 群体自主运行：由实际使用群体的非创始人成员完成部署、邀请、故障恢复与日常维护，记录遇到的问题和作者介入次数；文档修正后由接手者重放，不把作者代操作算作自主完成。按实际贡献逐步交接维护权限，不预设委员会或投票系统。

## 已知限制

写进产品说明，不设法绕过：

1. **当前不承诺应用关闭后的消息通知或投递。** 手机回来时只能同步仍由可达节点持有的消息；常在线成员也需要有人承担存储、带宽与维护。可选通知服务若以后设计，须写明依赖和缺失时的边界，不使其成为协议运行前提。
2. **底层依赖 Holepunch 的技术栈。** 当前保持该依赖；独立实现须列明复用的上游组件及其版本、协议资料和获取方式，不将第二个 UI 或封装同一核心称为独立实现。
3. **应用商店是中心化的。** 商店账号和备案主体与具体的人或公司绑定。
4. **语音通话没有中继兜底。** 打洞失败时无法接通；移动端不提供原生通话。
5. **公共中继不可信。** 它读不到内容，但能记录元数据，也可能拒绝转发。
6. **聊天尚无端到端加密，也不承诺匿名。** 签名用于校验来源，CID 用于校验内容；知道文件链接的人可发现做种者并获取其公网 IP，实测见[验证状态](validation-status.md)。
