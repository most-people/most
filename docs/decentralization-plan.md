# MostBox 长期方案与推进计划

更新日期：2026-11-16。基线：`dev` 分支 `e99f16c`。

本文记录负责人确认的长期目标、设计原则和推进顺序，供开发者和 AI 助手执行。与 `AGENTS.md`、`docs/roadmap.md` 冲突之处见文末「需要同步修改的现有文档」；在那些文档改完之前，以本文为准。

## 目标

MostBox 是开源的、完全去中心化的聊天与文件传输应用。**聊天第一，文件第二。**

项目要能长期稳定运行，即使创始人不在。参照物是磁力链接和 Clash：标识符自己能证明自己，没有任何一台必须存在的服务器，协议是任何人都能照着实现的文档，作者不是任何一层的依赖。

## 设计原则

1. **三个自证明的标识符，其余都由它们派生。**
   - 内容 = CID（UnixFS CID v1，与 kubo 一致）
   - 频道 = 一把随机密钥
   - 人 = 一把公钥
2. **一种角色：节点。** 在线的节点做三件事：做种它持有的文件，同步它加入的频道；公网可达且主人愿意时，替别人转发字节。手机是经常不在线的节点。不为"种子""中继""常驻节点"各建一套概念。
3. **没有必须存在的服务器。** 引导节点和中继都用同一种方式：安装包自带种子列表兜底，本机缓存见过的好节点，其余靠 DHT。官方服务器只是列表里普通的一员，任何分支改一行就能替换。
4. **知道即有权。** CID、频道密钥、未公告的中继公钥都是能力凭证：知道它就能用，不另建白名单或注册流程。
5. **升级一次，然后冻结。** 趁用户少，把所有不兼容的协议改动放进同一次升级。此后 `most://` 链接、topic 派生、消息签名格式不再修改，只做新增。
6. **如实写明限制**，不绕过去。见「已知限制」。

## 工作方式

- 先读 `AGENTS.md`、`docs/cid-drive-protocol.md`、`docs/acceptance.md`、`docs/validation-status.md`、`docs/p2p-risk-boundaries.md`，遵守其中的开发约定。
- 在 `dev` 分支上按阶段顺序推进。每项单独提交，提交前运行 `npm run format`。
- 每项完成后报告：改了什么、跑了哪些检查、哪些没有验证及原因。
- 标了【先设计】的项：只写设计文档并提交，然后停下等负责人确认，不写实现。
- 量化门槛先提交、再测试，不得事后修改。验证结果写入 `docs/validation-status.md`，原始日志放 `docs/evidence/`。
- 标了【待核实】的技术前提必须先读依赖源码或写最小实验确认；不成立就写明限制并停下，不自行发明替代协议。
- 不做本文之外的重构、功能或清理。

## 阶段 1：协议规范

目标：写出一份别人能据此实现第二个客户端的规范。它是项目能在创始人之外延续的那份文件。

1.1 新建 `docs/protocol/`，先如实描述**当前** `dev` 的行为，不夹带改动：

- 标识符：CID 参数（CID v1、raw leaves、256KiB 分块、每层 174 个子节点、balanced）、`most://` 链接语法、频道 ID 与频道 key、账号密钥与设备证书。
- 发现：文件 topic 与频道 topic 的派生、DHT 引导。
- 连接：Hyperswarm 握手、中继的使用条件。
- 文件传输：`most-cid-drive/2` 的 `want` / `have`、drive 内路径、下载后校验。
- 聊天：频道持有证明、hello、writer core、消息字段、排序与去重。
- 语音信令：`join` / `state` / `heartbeat` / `leave` / `signal`。

1.2 写到线上字节这一层：每条消息给出编码和示例，使协议不依赖 Holepunch 技术栈的具体实现细节来理解。

1.3 测试向量：`docs/protocol/vectors/` 放机器可读的样本（CID 黄金样本、链接解析、topic 派生、消息编码），并让桌面和移动端的测试都读取同一份文件。

验收：规范中每条陈述都能指到代码位置；测试向量在两端测试中通过。

## 阶段 2：一次性升级，然后冻结

所有不兼容改动合并为一个版本发布，与尚未发版的 CID drive v2 一起。各项【先设计】，设计文档放 `docs/protocol/`，全部确认后再统一实现。

2.1 【先设计】版本协商与信封

- 协议名、topic 派生和消息都带版本或域分隔。
- 消息外层信封带版本号；遇到不认识的字段和消息类型时忽略而不报错。
- 目标：此后新增能力（例如加密）不需要全体同时升级。

2.2 【先设计】文件 topic 单向化与 `want` 证明

- topic 改为带域分隔的单向哈希，DHT 上看到 topic 的人无法反推 CID。
- `want` 必须证明请求者知道 CID 摘要，而不只是知道 topic；可参考 `server/src/core/channelHello.js` 的 challenge + HMAC，并绑定连接双方公钥防重放。
- 只知道 driveKey 的人能否通过列目录得到 CID；如果能，评估用摘要派生的密钥加密 drive 内容。
- 补攻击测试：仅凭 topic 无法下载。
- 写明改动后 DHT 上仍然可见的信息，同步 `PRIVACY.md`。

2.3 【先设计】聊天消息签名

- 用设备密钥对规范化后的消息签名；消息如何携带或引用设备证书；接收端如何验证到账号地址。
- 规范化序列化的精确定义，桌面与移动逐字节一致，附测试向量。
- 证书过期、设备更换的处理；系统消息与成员资料事件是否签名。
- 账号密钥由用户名和密码派生，没有服务器限速，弱密码可被离线穷举；签名生效后这等于可以冒充他人。设计中给出处理办法。

2.4 【先设计】频道密钥

- 频道凭证改为高熵随机密钥，topic 由它派生。
- 频道 core 不再出自公开的共享主密钥。
- 自定义短 ID 的去留：取消，或明确标为公开频道。
- 至少把密钥派生定死，使端到端加密以后可以作为新增能力加入；评估是否在本次升级中直接实现加密。

2.5 语音信令格式写入规范，随协议一起冻结，使以后更换音频传输方式不破坏兼容。

2.6 实现与发布

- 全部设计确认后统一实现，桌面与移动同时完成，`npm run test:cross-core` 覆盖双向互通。
- 旧数据的一次性迁移方式参照 `docs/cid-drive-protocol.md` 的做法。
- 发布后在 `AGENTS.md` 写入冻结声明：链接格式、topic 派生、签名格式只增不改。

## 阶段 3：去掉对创始人的依赖

本阶段是纯新增，不改已冻结的协议，可以与阶段 2 的设计并行准备。

3.1 中继选择

- 【待核实】Hyperswarm 的 `relayThrough` 是否接受函数、能否按连接选择并在失败后回退。
- 选择顺序：用户配置的中继（自己的、好友给的）→ DHT 上公告的 → 安装包自带的种子列表。
- 连不上就换下一个，本次运行内不再使用；本机记住好用的，下次优先。
- 提供"只使用我配置的中继"开关。

3.2 节点成为中继

- 默认关闭，用户主动开启；开启前说明带宽消耗、能看到他人 IP、所在地区可能的法律风险。
- 只有公网可达的节点才能开启，复用已有的可达性检测。
- 公开：在固定的 DHT topic 上公告。私有：不公告，由用户把公钥交给好友。
- `scripts/blind-relay.js` 增加并发会话上限、单个对端会话上限和每会话流量上限，默认值按聊天流量设定并写明依据。

3.3 引导节点

- 【待核实】HyperDHT 是否支持持久化已知节点并用于下次启动、公网 MostBox 节点能否充当引导节点。
- 种子列表可配置；本机缓存见过的好节点。

3.4 移动端

- 中继公钥不再是独立常量；与桌面使用同一套配置和选择逻辑，并可关闭。

3.5 语音

- STUN 地址改为可配置。
- 打洞失败时给出明确提示。

3.6 其他依赖清点

- 列出所有指向创始人或官方服务器的环节（更新检查、下载地址、域名、默认允许的来源等），逐项改为可配置或可缺省，缺失时功能降级而不是失败。

3.7 文档

- `docs/p2p-risk-boundaries.md` 新增志愿中继一节：性质、志愿者的风险、坏中继能做和不能做的事。
- `PRIVACY.md` 写明：公共中继可能由任何人运营，能看到双方 IP、公钥、时间和流量，看不到内容；大量假中继占据公告的风险。
- 大陆商店版是否允许"成为中继"和"使用公共中继"，在合规评估中确定。

验收：关闭官方中继和官方引导节点后，用志愿节点重跑 F5 的 netns 对称 NAT 条件并达到原门槛。

## 阶段 4：聊天可靠性验收

4.1 按 `AGENTS.md` 的量化门槛建立聊天统计：随机断连、分区、重启注入不少于 100 轮，C1–C4 零违例，分区恢复后收敛时间 P95 不超过 30 秒。

4.2 C5：明确并测试"其他成员全部离线时能读到的历史"。写明常在线节点代收消息的边界：它是频道成员，能读到内容。

4.3 文件验收遗留项：

- F2 坏对端桩：截断、极慢、谎报大小，并测量代价。
- 移动核心的崩溃注入，覆盖范围对齐 `npm run test:crash`。
- 逐连接记录实际路径（直连 / 打洞 / 中继）。
- 排查 real-wifi 重装后第一轮"有 peer 但 0 字节"的失败：先写出复现测试，复现不了就记录已排除的原因。
- 蜂窝与网络切换。

## 阶段 5：整理与分发

5.1 Web3 工具箱移出主仓库。账号密钥派生和设备证书依赖 secp256k1 相关代码，移出时不得影响身份与认证；先列出依赖关系再动手。

5.2 抽出共享协议模块：只搬两端都有的纯函数（CID 与 topic、`most://` 解析、协议消息编解码、频道帧），一次一个模块，不改行为，不拆 `server/src/index.js` 的引擎类。

5.3 统一 `ipfs-unixfs-importer` 版本。先查明移动端停在 17.0.1 的原因；不能统一就把原因写进 `AGENTS.md`。

5.4 分发：源码、可复现的构建和可直接下载的安装包是项目的正本；应用商店版是分发渠道之一，不作为项目存续的前提。

## 暂不做

- 边下载边按块校验、多源并行下载。
- 移动端原生实时通话。
- 让音频走已有的 Hyperswarm 连接（方向保留；【待核实】底层是否支持不保证送达的消息）。
- 公开的内容目录、搜索、官方长期做种，继续遵守 `docs/p2p-risk-boundaries.md`。

## 已知限制

写进产品说明，不设法绕过：

1. **手机关闭应用后收不到消息。** iOS 后台推送需要有人运营推送服务器，与完全去中心化冲突。消息留在常在线节点上，手机打开时同步。
2. **底层依赖 Holepunch 的技术栈。** 现在不更换；规范写到字节层，为将来更换底层而不更换协议留出可能。
3. **应用商店是中心化的。** 商店账号和备案主体与具体的人或公司绑定。
4. **语音通话没有中继兜底。** 打洞失败时无法接通；移动端不提供原生通话。
5. **公共中继不可信。** 它读不到内容，但能记录元数据，也可能拒绝转发。
