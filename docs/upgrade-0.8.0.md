# MostBox 0.8.0 升级说明（自建节点）

本文面向自建 MostBox 节点、并通过 `https://most.box/chat/join#<token>` 邀请链接接入聊天的客户。适用于**从 0.5.x 直接升级到 0.8.0**（生产节点的唯一升级路径）。0.6.0 / 0.7.0 只在测试环境出现过，其数据不做迁移：测试节点请从 0.5.x 备份重新部署，或清空后安装 0.8.0。

版本范围说明（2026-11-21）：本文只描述所列版本已有升级路径。项目早期不承担历史版本兼容，此前“0.8.0 是最后一次不兼容升级”的承诺已撤销；未来升级或迁移按具体版本单独说明，见[早期协议兼容策略](decentralization-plan.md#早期协议兼容策略)。

## 已在 0.8.1 的节点升级到 0.8.2

0.8.1 → 0.8.2 协议与数据格式不变，无需迁移、无需约维护窗口：停止节点，换成 0.8.2 程序（Docker 镜像 `ghcr.io/most-people/most-box:0.8.2`），用原数据目录和配置启动即可。`/api/node/status` 的 `version` 应为 `0.8.2`。

0.8.2 起节点**不再做任何请求限流**（0.8.1 在 CDN / 网关后会因所有访客共用一个来源地址而误把正常用户限流，表现为发消息后页面报错、请求返回 429）。因此请注意：

- **邀请码请使用长随机串**，例如 `openssl rand -hex 16` 生成的 32 位十六进制；不要使用短的或可猜测的邀请码。节点不再限制猜测次数。更换邀请码后，邀请链接里的 `node_invite` 也要同步更换。
- 防刷请在节点前面的网关或 CDN（如 Cloudflare）上配置。

## 概要

0.8.0 实现了 MostBox 协议 v2：

- 聊天：每条消息、成员资料、在线状态和语音信令都由用户设备签名，节点无法再冒充用户发言。
- 文件：DHT 上公布的文件 topic 无法还原出 CID；只有知道 CID 的人才能从做种节点拿到下载所需的密钥。
- 同一 v2 版本内的可选能力按连接协商；不承诺未来协议版本继续与 v2 互通。

**这是一次不兼容升级。** 0.8.0 与 0.5.x 的节点和网页之间，聊天和文件都不互通。所以需要约定一个维护窗口：您升级自建节点的同时，我们切换 most.box 网页。

## 升级后用户会看到的变化

| 项目     | 变化                                                                                                                                                                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 登录     | 用户照常打开邀请链接即可。首次进入时自动迁移到新的聊天身份，无需额外操作。旧版保存在浏览器里的登录会失效：直接打开收藏的聊天页面会看到空列表，需从邀请链接重新进入；用账号密码登录的网页用户需重新登录一次（页面不会主动提示，点「加入聊天」会出现登录框）。                       |
| 聊天身份 | 聊天身份与钱包分离，**聊天地址会改变**；钱包地址不变。如果您的系统保存了用户的聊天地址，请按新地址更新。                                                                                                                                                                           |
| 历史消息 | 升级前的文字消息保留为只读，每条在时间旁带小号「未签名」标记（作者名是旧版自填的，存放在本节点，仅本节点可读）。旧消息无法确认是谁发的，所以自己发过的旧消息也显示在左侧。只有升级时已在频道里的成员能看到；**升级后新加入的成员看不到旧消息**。旧版的「加入了群聊」提示不再显示。 |
| 旧附件   | 升级前聊天里的文件、图片附件，在历史中显示为一行 `most://` 链接文本，不能在聊天里直接点开。文件本身仍在节点上，可在文件库中找到并打开。                                                                                                                                            |
| 频道     | 邀请链接里的频道 ID（如 `005c8db8d4914eb2` 这类自定义 ID）会成为「公开频道」：知道 ID 的人都可以加入并阅读，这与原来的实际情况相同。通过邀请链接进入的用户看不到频道 ID 和这条提示（与 0.7.0 相同）；用账号密码登录或使用 App 时，频道详情中会注明。新建私密频道会使用随机凭证。   |
| 文件     | 文件列表、`most://` 分享链接和文件内容都保留，按 CID 下载和校验的方式不变。首次启动时节点会把所有文件搬到新的存储位置（见下文的时间与磁盘）。                                                                                                                                      |
| 设备授权 | 登录后默认授权 30 天，可在个人资料中改为 4 小时或 1 天（如需要会再次验证密码）。到期前会提示续期。邀请链接进入的身份自动续期。                                                                                                                                                     |
| 首次进入 | 进入时身份计算约需 0.5–1 秒，手机浏览器上页面会短暂没有响应，属于正常现象。                                                                                                                                                                                                        |

## 使用 MostBox App 的用户

如果有用户通过 MostBox 安卓 App（0.5.x）使用本机节点，或把 App 连接到您的节点：

- 升级 App 后，旧登录失效。App 启动时仍优先连接上一次使用的远程节点（连不上才回到「本机节点」），需在「我 → 节点与做种 → 管理连接」中**重新登录**（同一用户名和密码）；如果当时在本机节点，登录后再连接远程节点。
- 重新登录时 App 会签署旧账号到新身份的迁移，连接远程节点后节点上该用户的文件、频道成员身份自动转到新地址。较旧的手机上这次登录约需 1 分钟（计算旧账号密钥），期间显示「正在登录」，请勿退出。
- App 本机节点里的文件会自动迁移并继续做种；本机频道的旧消息保留并带「未签名」标记，频道显示原来的名字。

## ST 后端是否需要修改

- **只生成邀请链接**：链接格式和生成代码不变（见 [ST 邀请集成](st-chat-join-integration.md)），不需要修改。
- **自行调用 WebSocket / HTTP 聊天接口**（不经过 most.box 网页）：需要按新版[原生聊天协议](native-chat-protocol.md)改为提交签名消息，旧格式的请求会被拒绝。如有这种情况请提前告诉我们。

## 迁移时间与磁盘空间

首次启动时，节点把每个文件从旧的共享存储复制到本节点自己的存储，重算 CID 校验后删除旧数据。实测（Windows 11、NVMe 固态盘，31 个文件共 1.97 GB，最大单文件 1.2 GB）：

| 项目                   | 实测                                         |
| ---------------------- | -------------------------------------------- |
| 启动到全部文件恢复做种 | 16 秒（约 8 秒/GB）                          |
| 迁移期间数据目录峰值   | 4.13 GB（升级前的 **2.1 倍**）               |
| 迁移结束后数据目录     | 3.42 GB（1.73 倍）：旧数据删除后空间暂不回收 |

估算方法：

- **时间**：按每 GB 约 8 秒估算，机械硬盘或网络存储请按 5–10 倍预留。文件越多越慢；迁移期间节点已可登录，尚未迁完的文件暂时不做种。
- **磁盘**：除备份（与数据目录同样大小）外，迁移还需要再预留**数据目录大小的 1.2 倍**空间。也就是说，升级前可用空间至少为数据目录的 2.2 倍。
- 迁移结束后数据目录约为原来的 1.7 倍：旧数据已删除，但占用的空间不会立即回收（实测对存储做一次整理后降到 1.34 倍，0.8.0 不会自动做这一步）。请按 1.7 倍规划长期占用；确认升级成功后删除备份可腾出 1 倍空间。

`node-holdings.json` 等记录文件中旧的 `topic`、`driveName` 字段不会被改写；0.8.0 每次都按 CID 重新计算，不使用记录里的值。

## 升级前准备

1. 与我们约定维护时间。窗口内您升级节点，我们切换 most.box 网页。
2. 确认服务器时间已开启 NTP 同步。签名有效期按节点本机时间判断，时钟不准会导致登录失败。
3. 确认数据目录位置和磁盘空间：
   - 数据目录默认是 `~/most-data`，配置文件在 `~/.most-box/config.json`；配置了 `dataPath` 的以实际值为准。
   - 可用空间至少为数据目录大小的 2.2 倍（备份 1 倍 + 迁移 1.2 倍，见上文）。
   - 备份**必须和数据目录在同一个文件系统上**（原因见「回滚方法」）。
4. 建议先在测试节点上用 0.5.x 的数据完整走一遍下面的步骤和验收。

## 升级步骤

以下以 Linux、数据目录 `/data/most-data` 为例，请替换成您的实际路径。

1. **记录当前状态**：记下当前节点版本，可在 `/api/node/status` 查看 `version`（远程访问需带 `x-mostbox-invite` 请求头），并记下 `holdings` 数量。
2. **停止节点**：暂停业务写入后，正常停止节点进程（例如 `pm2 stop <name>` 或 `systemctl stop <service>`），确认进程已退出。不要在节点运行时复制数据目录。
3. **备份数据目录和配置**（同一文件系统上）：

   ```bash
   cp -a /data/most-data /data/most-data.bak-before-0.8.0
   cp -a ~/.most-box ~/.most-box.bak-before-0.8.0
   ```

4. **安装 0.8.2**：0.8.0 未单独发布，请安装 0.8.2（包含 0.8.0 的全部内容，协议相同）。按您原来的方式（npm / Docker 镜像 `ghcr.io/most-people/most-box:0.8.2` / 安装包）换成 0.8.2。**继续使用原来的数据目录**（不要让新版直接打开备份副本），配置保持不变。
5. **启动节点**：首次启动会自动迁移文件和频道记录，日志中每个文件会出现 `Migrated <cid> to its own seed drive`。按上文估算的时间等待，期间不要强制结束进程（被意外中断也可以直接重新启动，未完成的文件会重新迁移）。
6. **检查版本**：`/api/node/status` 中的 `version` 应为 `0.8.2`，`holdings` 数量与升级前相同、没有 `error` 状态。
7. **通知我们**：我们切换 most.box 网页后，由您用邀请链接做下面的验收。

## 升级后验收

请用升级前就存在的客服账号和用户账号，通过邀请链接进入，逐项确认：

- [ ] 能正常进入频道
- [ ] 能看到升级前的文字消息，带「未签名」标记
- [ ] 频道详情中成员人数正确（邀请链接用户看不到频道 ID 与公开频道提示，属正常）
- [ ] 文件库中能看到升级前的文件，任选一个能打开
- [ ] 客服与用户能互相收发新消息（对方重新进入频道后可见），新消息没有「未签名」标记
- [ ] 节点上没有处于错误状态的文件记录

全部通过后再恢复正常业务。

## 回滚方法

数据目录里的 `CORESTORE` 文件是存储设备标记，里面记录了这个文件自身的 inode。**直接把备份目录复制回去是无法启动的**（会报「存储文件损坏」）。回滚时要把原目录里那个 `CORESTORE` 文件移动（不能复制）到恢复后的目录中。

如果验收不通过：

1. 停止新写入，停止 0.8.0 节点，并通知我们回退 most.box 网页。
2. 保留升级后的目录，恢复备份，并移回原 `CORESTORE` 标记文件：

   ```bash
   mv /data/most-data /data/most-data.after-0.8.0
   cp -a /data/most-data.bak-before-0.8.0 /data/most-data
   mv /data/most-data.after-0.8.0/CORESTORE /data/most-data/CORESTORE
   rm -rf ~/.most-box && cp -a ~/.most-box.bak-before-0.8.0 ~/.most-box
   ```

3. 换回 0.5.x 程序并启动，用邀请链接确认旧消息和文件都在。

注意：

- **不要用 0.5.x 程序直接打开已经迁移过的数据目录**，迁移是单向的，存储格式也已由新版改写。
- `mv` 只有在同一文件系统内才会保留 inode；跨磁盘的备份无法按上面的方法恢复。
- 切换后新产生的消息会留在 `most-data.after-0.8.0` 中，回滚后旧版不可见，请不要删除该目录。

## 其他说明

- 节点默认不配置中继。如需中继，请在节点配置中自行设置 `relayPublicKey`。
- 知道文件 CID 的人仍可以通过 DHT 查到正在做种的节点 IP；只看到 DHT 上 topic 的人无法再还原 CID。详见隐私说明。
- 升级过程中有任何异常，请保留节点日志并与我们联系。
