# 群聊模型与消息承诺

更新日期：2026-11-22。本文集中维护群聊产品规则与实现差异，服务于[公共协议长期目标](decentralization-plan.md)。现行线上协议仍按 [v2 规范](protocol/v2/README.md)执行；以下分页与清理设计不代表功能已完成。

## 已确认的群模型

- **所有成员只有普通用户一种群内身份。** 创建者没有额外权限，不设群主或管理员，不引入管理员任免、按管理角色踢人或强制撤回他人消息的机制。消息仍由各自身份签名。
- **用户只使用一个 `channelId`。** 它同时标识群并作为加入凭据；创建、分享和输入的都是同一个值，没有额外的邀请码或邀请凭证。
- **知道即有权。** 知道 `channelId` 即可尝试加入、读取历史和发言；不另设入群审批或成员白名单。
- **随机且保密用于私密交流，容易猜到或主动公开用于公开讨论。** 可猜的公开群是允许的使用方式；界面须如实说明公开边界。这里的私密指加入凭据的保密，不承诺端到端加密或匿名。
- **泄露后换群。** 新建全新随机 `channelId` 的群，通过可信方式分享给希望继续交流的人。旧群仍存在，旧副本不能收回；新群从空历史开始，不自动把旧签名消息变成新群历史。

“普通用户”是群内权限模型，不影响节点运维、远程节点认证或现有管理台的访问控制。

## 历史、维护与失败体验

- **历史平权。** 成员有权取得群内全部仍可获取的历史，包括加入前的消息，不按加入时间或是否运行常在线节点区分。实际可获取范围取决于仍持有数据且可达的节点，不承诺永久保存。
- **文字历史默认全部同步保存，界面分页，附件点击时下载。** 同步范围是仍可获取的全部历史，不设最新 1000 条的同步或保留上限。加入群、同步历史、滚动消息列表不自动下载附件内容；用户点击附件才触发获取，本地已有可校验读取的同一 CID 时直接打开。图片、语音等附件适用相同原则，预览不得隐式拉取完整附件。
- **下载后默认继续做种。** 附件下载完成须按 CID 校验，成功后持续做种，沿用既有文件规则。消息中存在 `most://` 链接不代表附件仍有在线种子；下载失败如实说明并提供重试。
- **维护自愿。** 存储、带宽和在线时间由成员志愿承担，可以退出；承担维护不增加群内权限，也不要求每位成员保持在线。
- **群体自行维持可用性。** 建议由群内愿意维护的成员自建常在线服务器节点，加入群并保存、同步文字消息，帮助错峰上线的成员补齐消息；不要求每位成员自建服务器，也不以服务器作为加入群的权限门槛。服务器上的节点仍是普通成员，其他成员持有的副本也能继续接力。
- **可用性取决于可达副本。** 发送者离线后，其他成员可从仍持有消息且可达的节点补齐；没有可达副本时，等待持有者再次上线，不承诺随时送达或永久保存。纯中继只转发连接字节，不等于加入群保存消息的节点。服务器节点也沿用附件按需规则，不因常在线而自动下载全部附件。
- **失败如实告知并引导。** 区分本机已保存、连接或同步受阻、历史缺块、附件暂未发现在线种子等实际情况；依据证据说明原因，提供等待、重连、重试或联系数据持有者等适用操作。不以超时推断数据已永久消失。

## 历史分页设计

**同步与显示分开：节点持续同步可获取的全部文字历史，界面首次读取最新 100 条，向上翻阅时每次读取更早的 100 条。** 100 是界面读取批量，不是协议限制、保存上限或用户需要配置的选项；不把全部历史一次性传给界面或一次性渲染。

- 复用现有历史接口的 `before` / `nextCursor` 游标语义，按稳定消息位置向前翻页；不新增一套 P2P 分页协议。内置节点也应提供相同语义，避免新消息到达后按数组偏移翻页导致边界移动。
- 实时消息、历史页与重连补齐结果按现有消息身份合并去重，保持目标版本的排序规则；加载旧页时保留阅读位置，翻页失败保留已显示内容并允许重试。
- 游标结束只表示当前节点在该次读取时没有更早的可读消息，不表示全群历史已同步完整。迟到历史和断线恢复后须重新检查已加载范围，补齐落在分页边界之间的消息，不能只刷新最新一页就宣称没有遗漏；缺块读取不得等待离线作者。
- 本次只定义读取和展示行为，不新增文字淘汰、保留期限或自动清理规则。全部同步仍受可达副本和实际空间约束；空间不足按[主动清理规则](#空间不足与主动清理)处理。

已有基础：HTTP `/api/channels/:name/history` 支持游标，接口默认 50、单次最多 100；设计中的客户端显式请求 100，不改变接口默认值。移动端远程模式已有按 100 条翻页入口，内置模式仍使用 `offset`，Web 主聊天仍读取消息列表；全端一致性、迟到历史补齐和性能尚未验收。接口说明见[聊天传输协议](native-chat-protocol.md#channels-and-history)。

## 数据自管与节点更换

2026-11-22 确认：**身份与数据由用户自己保管，远程节点可以更换。** 原节点永久下线或运营者不再配合时，用户仍应能凭自己保存的材料恢复并继续使用。

- **身份由用户控制。** 身份恢复材料由用户自行保管；换节点后保留原身份，不依赖旧节点运营者批准或提供材料。
- **保管与产品责任明确。** 用户负责保管，产品负责让保存、备份与恢复足够简单。日常消息默认在本机保存，用户可以主动导出备份并在新设备恢复；备份界面须清楚说明保存了什么、还需要保管什么，不能让用户把只有身份或目录的备份误认为完整内容备份。
- **身份全部丢失就重新建立。** 所有身份恢复材料和可用设备都丢失时，用户重新建立身份，官方没有重置原身份的权限。有消息或文件副本不等于能够恢复原身份；尚有可用设备或恢复材料时，不应误导用户放弃原身份。
- **群入口可带走。** 用户自行保存已加入群的 `channelId`，换节点后仍能进入原群，沿用既有群权限规则。
- **已有内容自己持有。** 文字历史默认同步到用户自己的设备保存；已下载文件也应有用户可保管的副本。连接远程节点不应把这些内容仅保存在远端。用户须能保存、导出和恢复这些已有内容，不能仅导出偏好或文件目录就宣称完整恢复。
- **恢复按实际副本说明边界。** 用户自己保存的消息和文件不应因旧节点消失而失效；未同步的消息、未下载的附件仍需从其他持有者获取，无任何可用副本时不承诺恢复。附件继续按需下载，不为自管要求自动下载所有附件。
- **先明确恢复方案再实现。** 本节是产品要求，保存、导出、身份恢复和换节点流程仍需设计与验收；不据此认定现有账号备份已经覆盖消息与文件。验收绑定同一目标版本，不新增历史版本兼容或迁移承诺。

## 空间不足与主动清理

2026-11-22 确认：**清理主要针对已下载附件，保留文字历史与附件引用。空间不足时明确提示，由用户主动清理，不静默删除已有聊天记录或文件。**

- 无法继续保存时，明确说明哪些操作或内容尚未保存，引导用户释放空间后重试；不得显示保存成功，也不通过自动删除已有内容腾出空间。
- 按 CID 清理用户选定的本机附件副本，停止本机对该内容做种；同一 CID 被多条消息引用时，一并说明影响范围。不要求其他节点删除，不等于全网撤回，也不删除用户另外保存到系统目录的副本。
- 清理后保留消息中的文件名、CID 与链接，显示未在本机保存；同步、翻页和重启均不自动重新下载。用户再次点击时才尝试获取，仍须校验 CID；没有其他可用副本时不承诺恢复。
- 当前不新增文字历史截断或删除后防回拉机制。附件清理入口、实际空间回收与失败恢复仍待设计和验收；坏数据与失败下载临时文件继续按既有规则清理。

## 收到与消息确认

**低优先级，暂不开发。** 保留以下产品规则，待后续明确安排时再设计和实现；收到回执不作为当前 MVP 的验收门槛。

已确认只显示**哪些用户收到**，不做已读。对方客户端收到消息就算，后台收到也算，无需打开聊天、让消息出现在屏幕上或下载附件。具体回执格式、认证与同步方式尚待设计和实现。

- 收到名单依据接收方回执，不能凭在线状态或任意中转节点持有消息推断某位用户收到。尚未收到回执只表示尚未确认，不能直接认定对方未收到。
- 收到不表示已读、已下载附件或承诺永久保存；文字默认同步保存、附件点击时下载仍按前述规则执行。
- 回执按 [envelope §7](protocol/v2/envelope.md#7-协议演进规则)明确目标版本与格式，再设计实现并覆盖断线重启；不为历史版本补回执兼容层。既有 C1–C5 和量化门槛保持不变，不能把产品“收到”状态直接替换为既有验收中“已确认”的定义。

## 本地屏蔽

2026-11-22 确认：**用户可以选择不显示某人的消息，只影响自己的界面。优先级很低，暂不安排新增或完善开发，保留现有实现。**

- 不影响其他成员接收和查看消息，不增加全群踢人或删除他人消息的权限，也不删除用户已经保存的内容。
- 本地屏蔽解决观看体验，不据此声称降低节点的同步、存储或带宽消耗；资源保护另行讨论。
- 现有客户端已有本地屏蔽与解除入口；证据适用范围以[验证状态](validation-status.md)为准，不把既有能力改记为尚未实现，也不据此认定全平台已验收。

## 已撤回的提案

2026-11-22 撤回“对节点运营者隐藏正文”的提案，不列入当前目标。将完整 `channelId` 交给远程节点，就应视为允许该节点读取群内容；数据自管与自由更换节点不构成对运营者保密的承诺。本次不引入仅能保存密文的授权能力，不修改现行协议的加密预留设计。

## 产品术语与现行实现的对应

用户只需一个 `channelId`。当前代码与 v2 协议仍保留内部派生值，下表描述现状，不构成未来保留旧命名或兼容层的要求：

| 上下文                                               | 含义                                                                                                   |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 产品中的 `channelId`                                 | 用户创建、分享、输入以加入群的同一个值；现行解析函数中对应 `handle`                                    |
| 现行 v2 的“频道凭证”                                 | 上述加入值的技术描述，不是用户还要取得的第二份凭证；随机群输入可解码为密钥，公开短名按现行规则派生密钥 |
| 现行 v2 的线上 `channelId` / 部分代码的 `channelKey` | 由群密钥派生的公开标识，用于签名绑定和协议寻址，不具备加入权限，不替代用户分享的值                     |

对应关系见 `server/src/core/channelKeysV2.js` 的 `resolveChannelHandle`、`channelIdFromKey` 与 [channel-keys §3](protocol/v2/channel-keys.md#3-派生)。本次不重命名线上字段，不改变 topic、密钥派生或签名覆盖范围；产品文档和 UI 不要求用户再提供一个值。

- 本地删除和屏蔽的范围与影响按前述规则执行；其他展示操作的具体需求另行讨论，不借此新增群内权限角色。
